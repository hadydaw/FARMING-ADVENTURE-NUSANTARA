| Kebutuhan | Sumber |

Versi dipatok (`4.7.2`) di `.github/workflows/android-build.yml` dan `project.godot` agar build dapat direproduksi. Pembaruan versi engine = entri keputusan baru.

## 3. Rendering

- Renderer **GL Compatibility** (OpenGL ES 3.0) untuk desktop dan mobile.
- Gaya 3D stylized: material tanpa specular, warna datar/toon, bayangan sederhana; hindari efek berat (SDFGI, SSR, volumetrik tidak tersedia di Compatibility dan tidak dibutuhkan).
- Model: glTF 2.0 `.glb`; tekstur dikompres ETC2/ASTC (diaktifkan di project settings).
- **Anggaran performa awal (usulan, diukur ulang di perangkat nyata):** target 60 FPS, batas bawah 30 FPS di HP kelas menengah; karakter ≤ 5 ribu segitiga, monster umum ≤ 4 ribu, pohon/objek dunia ≤ 1 ribu; draw call ≤ 150 per frame; tekstur ≤ 1024 px untuk objek dunia.
- Ditinjau ulang bila art direction memerlukan Mobile renderer (Vulkan).
- Strategi performa adaptif (D-052) dirinci di §4ai; angka di atas tetap **usulan yang belum diukur di perangkat nyata**.

## 4. Struktur Kode dan Proyek

```
res://game/
  boot/      layar boot dan uji fondasi (BUKAN gameplay)
  core/      autoload & layanan lintas fitur: AppInfo, SaveService, BackendClient
  i18n/      translations.csv (id, en)
  data/      data game (item, tanaman, monster, ...) - kosong sampai desain selesai
  world/     wilayah, desa, dungeon - kosong
  ui/        antarmuka bersama - kosong
  assets/    models, textures, audio, ui, fonts
```

Prinsip arsitektur (berlaku saat gameplay mulai dibangun):

1. **Data-driven:** item, tanaman, monster, quest, rank, wilayah didefinisikan sebagai data (Resource/JSON), bukan hardcode, agar mudah diseimbangkan dan disinkronkan.
2. **Pemisahan:** logika game (aturan) terpisah dari tampilan; logika dapat diuji headless.
3. **Event bus** untuk komunikasi antarsistem (signal) agar sistem tidak saling mengunci.
4. **Region sebagai unit muat:** tiap wilayah adalah scene/paket sendiri yang dimuat-bongkar, mendukung Progressive World Unlock dan batas memori HP.
5. **Semua akses jaringan lewat `BackendClient`**; gameplay tidak memanggil HTTP langsung.
6. **Semua teks lewat kunci terjemahan.**

### 4i. Implikasi Arsitektur dari D-022 (hanya catatan; belum diimplementasikan)

Syarat utama: **jumlah NPC besar tetap terkelola** (kinerja di HP dan beban penulisan konten).

- **Sistem dialog:** teks lewat kunci terjemahan (id/en, §6), dialog bersyarat per hubungan/cerita; konten yang besar dipisah per NPC agar mudah dikelola dan diuji (validator data otomatis untuk kunci yang hilang, rujukan rusak).
- **Pencarian jalan dan pengaturan beban:** jumlah NPC aktif dibatasi oleh anggaran performa §3; navigasi memakai navigation mesh per area.
- **Save:** hubungan, flag cerita, kemajuan quest NPC, dan keadaan khusus NPC masuk payload save (skema berversi); jadwal tidak disimpan (diturunkan dari data + waktu).
- **Online (D-014):** NPC adalah progres pribadi; tidak ada sinkronisasi real-time.
- **Cakupan (diperbarui oleh D-066):** isi bagian ini (pertemanan/kepercayaan/reputasi) tidak diubah; model dapat diperluas dan romansa/pernikahan/keluarga/anak kini ditetapkan terpisah di D-066 (§4aw, hanya catatan).

### 4l. Implikasi Arsitektur dari D-025 (hanya catatan; belum diimplementasikan)

- **Ikan dan lokasi sebagai data:** spesies (habitat, kelangkaan, kebutuhan musim/cuaca/waktu, perilaku, hasil item), titik/zona memancing per wilayah, alat pancing, dan umpan sebagai data. Spesies atau lokasi baru = data baru.

- **Perkembangan desa:** variabel dunia (§4i/§4x) yang berubah oleh quest, event, dan tindakan pemain; NPC/fasilitas/jadwal bereaksi lewat kondisi data, sehingga perubahan tidak butuh kode khusus.
- **Konsistensi saat pindah wilayah/muat ulang:** keadaan NPC dasar = (jadwal, waktu game, seed, flag) sehingga posisi dapat dihitung ulang tanpa menyimpan jalur; hanya keadaan yang tak dapat diturunkan (kebutuhan, interupsi, hasil keputusan, hubungan, flag) disimpan di payload save (§5) berversi; muat ulang menempatkan NPC pada titik jadwal yang sah.
- **Online/cloud:** NPC adalah progres pribadi (D-014); tidak ada sinkronisasi real-time; cloud save lewat mekanisme save yang sama.
- **Lokalisasi:** nama NPC, peran, dan teks aktivitas lewat kunci terjemahan id/en (§6).
- **Pengujian:** uji headless simulasi jadwal 1 musim untuk semua NPC (tak ada yang terjebak atau tanpa lokasi valid), konsistensi posisi saat transisi LOD dan muat ulang, fallback, serta anggaran waktu CPU per frame di perangkat target nanti.

- **Kelas perangkat dan profil:** saat pertama jalan, klasifikasi heuristik ringan (RAM, GPU/driver, SoC/model bila tersedia, resolusi layar) menghasilkan **kelas awal** (mis. Rendah/Menengah/Tinggi); kelas menunjuk **preset grafis** (§6a, D-045) yang mengatur: skala render 3D dan resolusi internal, kualitas/jarak bayangan, jarak render/culling, kepadatan objek (vegetasi §4j, dekorasi §4n), kualitas partikel dan efek cuaca (§4q), anti-aliasing yang didukung Compatibility, batas FPS, serta tingkat LOD. Kelas dapat dikoreksi **berdasarkan pengukuran nyata saat bermain** (bukan benchmark berat di awal). Daftar perangkat/ambang diisi dari data uji nyata (D-049), bukan dari asumsi.
- **Penyesuaian dinamis (adaptive):** pengendali berbasis histeresis memantau frame time bergulir; bila melewati anggaran berkelanjutan turun satu tingkat pada **tuas berurutan** (urutan menunggu hasil profiling; prinsip: kurangi yang paling murah terhadap identitas visual dahulu: bayangan, partikel, kepadatan vegetasi, jarak render, skala resolusi) dan naik kembali pelan bila stabil; perubahan memakai jeda dan pembatas agar tidak berayun (flapping) serta tidak terjadi saat momen kritis (combat/boss/dialog) kecuali darurat; **UI dirender pada resolusi asli** terpisah dari skala render 3D agar keterbacaan terjaga; elemen yang menjadi identitas visual (palet toon/outline gaya D-008, siluet karakter dan target interaksi §4v) tidak diturunkan di bawah ambang minimum keterbacaan. Pemain dapat mengunci preset manual (override, D-045) dan perubahan diumumkan lewat indikator ringan.
- **Frame pacing dan FPS:** target FPS adalah **data per kelas** (tidak ditetapkan); gunakan batas FPS yang stabil (mis. kunci 30 yang rata lebih baik daripada 60 yang goyah) dan `Engine.max_fps`/sinkronisasi layar sesuai dukungan; hindari hitch: tidak ada alokasi besar, pemuatan sinkron, kompilasi shader/pipeline mendadak, atau penulisan berkas di thread utama saat bermain; **pra-pemanasan (shader/material warm-up) di layar muat** untuk material yang dikenal; pekerjaan berkala disebar antar-frame (time-slicing) dengan **anggaran milidetik per frame per sistem** (AI NPC §4aa, simulasi dunia §4p/§4q, UI, audio, save §5a); proses fisika dengan langkah tetap dan batas iterasi.
- **CPU:** simulasi berbasis event dan selisih waktu (bukan per frame) di seluruh sistem (§4b, §4j, §4k, §4x, §4z); NPC berjenjang LOD dengan batas jumlah NPC penuh sebagai data per kelas (§4aa); pencarian jalan dan query (navigasi, target interaksi §4v) dibatasi frekuensi dan jumlah; pooling objek (peluru, efek, kerusakan, item jatuh) untuk menghindari alokasi; pemrosesan nonkritis ditunda ke frame lega atau thread pekerja bila aman; hindari `_process` pada objek yang tidak aktif (matikan proses node yang tidak terlihat/jauh).
- **GPU (GL Compatibility):** batching dan instancing (MultiMesh untuk vegetasi/rumput/objek berulang §4j), atlas tekstur dan material bersama untuk menekan draw call, kompresi tekstur ETC2/ASTC (§3), mipmap, **LOD mesh dan culling jarak/oklusi** (visibility range; region/chunk §4o), bayangan sederhana dan jumlah lampu dinamis rendah, tanpa efek pascapemrosesan berat, batas overdraw (partikel transparan), anggaran poligon dan tulang per karakter (§3, §4ab; penggabungan mesh kosmetik), kamera adaptif dengan jarak lihat per profil (§4t).
- **RAM dan memori:** anggaran memori per kelas perangkat (data); muat per **wilayah/chunk** dan bongkar yang tidak dipakai (§4o), pemuatan latar (`ResourceLoader` threaded) dengan prioritas dan batas konkurensi, **cache LRU bertanda ukuran** untuk resource sering dipakai dan pooling; hindari menahan referensi usang (siklus), pantau kebocoran node/resource di uji; streaming audio untuk musik panjang dan pemuatan SFX per wilayah (§4s); tekstur/audio terkompresi; mode **tekanan memori**: bila sistem memberi peringatan memori rendah (`NOTIFICATION_APPLICATION_*`/low-memory), bongkar cache nonkritis dan turunkan kualitas; **save paksa** sebelum aplikasi dimatikan sistem (§5a).
- **Pemuatan aset dan resource:** aset dikelompokkan per wilayah/fitur (sejalan §4ag), dependensi eksplisit, layar muat dengan pra-pemuatan dan pemanasan, hindari spike saat berpindah wilayah (muat wilayah tetangga di latar), format glTF `.glb` dan impor yang dioptimalkan, ukuran APK dan data tambahan diawasi di CI (§10a); aset khusus kelas rendah (tekstur resolusi turun, mesh LOD) lewat varian terkendali, bukan duplikasi seluruh aset.
- **NPC, AI, animasi, dan simulasi dunia:** mengikuti §4aa dan §4i (tiga tingkat LOD simulasi, time-slicing, evaluasi berbasis event); **LOD animasi**: pembaruan animasi dengan frekuensi lebih rendah untuk NPC jauh, berhenti untuk yang tidak terlihat, penghematan tulang/IK; animasi gabungan mount/karakter tetap ringan (§4ac); keramaian (festival/event §4p) memakai batas jumlah dan variasi murah; simulasi dunia (pertumbuhan §4j, ternak §4k, cuaca §4q) berbasis selisih hari saat jauh; hanya satu mount aktif penuh; jumlah musuh aktif combat/dungeon dibatasi anggaran (§4a, §4c).
- **Baterai dan termal:** pembatas FPS dan opsi **mode hemat baterai** (FPS dan skala render lebih rendah, partikel dikurangi) sebagai preset; pemantauan **suhu/status termal** lewat API Android (mis. thermal status/headroom bila tersedia) dan status baterai; pada status termal tinggi atau baterai rendah, PerfService menurunkan tingkat secara bertahap **dan memberi tahu pemain** (indikator ringan, kunci terjemahan §6); jaringan hemat: sinkronisasi dikelompokkan dan tidak terus-menerus (§5a), unduhan hanya Wi-Fi sebagai opsi (§4ag); layar mati/aplikasi latar belakang: hentikan simulasi, render, dan audio nonesensial; tidak ada kerja latar belakang berat; kecerahan dan haptik tidak dikelola agresif (pengaturan pemain).
- **Perangkat berbeda:** pencarian dukungan dengan prinsip **degradasi bertahap** (semua fitur gameplay tetap tersedia di semua kelas; hanya presentasi yang berubah), uji layout pada beragam rasio dan resolusi (§4r), penanganan GPU/driver bermasalah lewat daftar penyesuaian data (workaround per perangkat bila ditemukan oleh uji nyata), dukungan minimum (RAM, versi Android) ditetapkan dari data uji; arm64-v8a saja (O-001).
- **Instrumentasi dan observabilitas:** overlay debug (FPS, frame time p50/p95/p99, memori, draw call, objek, NPC aktif, suhu) hanya di build dev; log performa ringkas per sesi uji; skenario beban baku (wilayah terpadat, banyak NPC, cuaca ekstrem, combat ramai; §10a) untuk perbandingan antar build; telemetri performa pemain menunggu keputusan privasi/akun (P-006, PENDING) dan tidak diasumsikan.
- **Pengujian dan bukti (D-049):** laporan performa dicatat dengan **sumber bukti** (CI-headless, emulator, perangkat fisik oleh pengguna/tester); angka dari CI atau emulator **tidak** dipakai sebagai klaim performa perangkat fisik; target dan ambang ditulis sebagai **usulan sampai diukur**; regresi performa (waktu muat, ukuran, frame time sintetis) menjadi bagian CI dan release gate (§10a); P-005 tetap menunggu laporan pengguna.
- **Hubungan dengan keputusan lain:** pengaturan grafis pemain dan profil (§6a) adalah antarmuka ke PerfService; update konten (§4ag) wajib menyertakan laporan regresi performa; keamanan/validasi (§5b) tidak boleh menambah beban per frame (dikerjakan di jalur asinkron); monetisasi (§4af) tidak memengaruhi performa/penurunan kualitas.
Tidak ada perubahan kode atau pipeline akibat keputusan ini.

### 4aj. Implikasi Arsitektur dari D-053 (hanya catatan; belum diimplementasikan; semua angka usulan dan belum diukur)

Memperdalam streaming wilayah di §4o dan anggaran/strategi memori di §4ai. Prinsip: **tanpa stutter dan tanpa lonjakan RAM** lebih penting daripada tampak mulus; bila ragu, gunakan loading screen.
- **Dua jenis transisi sebagai data per tautan (`Transition`):** (1) **Streaming** (wilayah luar yang berdekatan, tanpa layar muat) dan (2) **Loading** (dungeon §4c, interior §4n, wilayah khusus, fast travel §4o, teleport cerita). Tiap tautan antarwilayah menyatakan jenisnya, titik masuk/keluar, syarat akses (kondisi §4x, aturan medan/mount §4ac), dan perkiraan beban; jenis dapat diturunkan ke Loading oleh PerfService (§4ai) untuk kelas perangkat rendah **tanpa mengubah konten**. Sistem lain bergantung pada antarmuka transisi, bukan pada jenisnya.
- **World Streamer:** pengelola chunk berdasarkan posisi pemain (dan arah gerak/kecepatan mount §4ac) dengan tiga cincin: **aktif** (dimuat penuh dan disimulasikan), **penyangga** (dimuat di latar, tidak disimulasikan/tidak terlihat), **tak dimuat**. Ukuran chunk, radius cincin, dan jumlah chunk maksimum adalah **data per kelas perangkat** (§4ai), ditentukan dari pengukuran nanti. Histeresis pada ambang muat vs bongkar mencegah muat-bongkar berulang di tepi chunk; prioritas memuat mengikuti arah gerak; di dalam wilayah besar (§4o) memakai chunk, di antar wilayah memakai tautan transisi.
- **Pemuatan asinkron bertahap:** `ResourceLoader.load_threaded_request` dengan batas konkurensi dan prioritas; pekerjaan di thread utama (instansiasi scene, penambahan node, pembuatan navigasi/collision) dipecah menjadi **potongan kecil per frame** dengan anggaran milidetik (time-slicing, §4ai) agar tidak hitch; urutan: data dan kolisi/navigasi dahulu agar pemain tidak jatuh/menembus, lalu mesh/material, lalu hiasan dan efek; objek dekoratif yang telat boleh muncul bertahap (fade-in) tetapi **permukaan yang dapat dipijak dan objek interaktif harus siap sebelum pemain dapat mencapainya** (jika belum siap, pemain ditahan/diperlambat oleh penghalang lunak atau transisi dialihkan ke Loading).
- **Gerbang kesiapan (readiness gate):** setiap tujuan transisi punya daftar syarat siap (kolisi, navigasi, titik masuk, objek wajib, audio ambience, NPC/LOD awal §4aa); transisi selesai hanya setelah semuanya siap atau batas waktu tercapai (lalu fallback: tetap di layar muat, ulangi, atau kembali ke titik aman). Pemain tidak dilepas ke dunia yang setengah termuat.
- **Loading screen:** adegan ringan sendiri (tanpa memuat aset berat), memakai tema UI terpusat (§4r); **ilustrasi** dari kumpulan data per wilayah/tema (tanpa teks tertanam pada gambar; teks seluruhnya lewat kunci terjemahan id/en, §6); **tips** dari data dengan kategori, syarat konteks (wilayah, progres, fitur yang sudah dibuka) dan pembatas agar tidak berulang cepat dan tidak membocorkan spoiler; selaras tutorial dan buku bantuan (§4ad); **indikator progres** berbasis kemajuan nyata gerbang kesiapan (bukan animasi palsu) atau indikator tanpa angka bila progres tak pasti; ditampilkan hanya jika transisi melewati ambang waktu kecil (menghindari kedipan layar muat pada beban singkat); transisi masuk/keluar memakai fade ringan; landscape dan safe area (§4r). Kontrol dan HUD dinonaktifkan atau disederhanakan selama muat; penolakan input tidak menumpuk (antrean dibersihkan).
- **Kesinambungan kamera dan audio:** kamera (§4t) mempertahankan orientasi saat transisi streaming (tanpa lompatan) dan menetapkan profil baru setelah pemain berada di titik masuk; pada Loading, kamera dipindah ke titik masuk **sebelum** fade-in; musik/ambience (§4s) crossfade antarwilayah dan dijeda/diteruskan dengan jelas selama layar muat; cuaca/waktu (§4q, §4b) tetap berjalan konsisten (waktu game tidak melonjak karena lamanya pemuatan; bila perjalanan memakan waktu kalender, dihitung lewat layanan kalender §4o).
- **Manajemen resource dan memori:** semua scene/resource dimiliki oleh **ResourceManager** dengan penghitungan referensi per wilayah/chunk dan dependensi eksplisit; **pelepasan otomatis** setelah chunk/wilayah keluar dari cincin dengan jeda (grace period) agar tidak muat-bongkar berulang; resource bersama (material, atlas, audio umum) dipertahankan di **cache LRU berbatas ukuran** (§4ai) dan dibagi antarwilayah; aset pasca-pelepasan diverifikasi di uji (tidak ada kebocoran node/resource); penggunaan memori dipantau per cincin, dan pada **tekanan memori** (peringatan sistem/ambang) radius cincin menyusut dan cache dikosongkan, jika perlu transisi dialihkan ke Loading; mount/kecepatan tinggi memperbesar penyangga hanya bila anggaran memori memungkinkan, jika tidak kecepatan efektif dibatasi pada medan yang belum siap.
- **Konsistensi dunia saat dimuat/dibongkar:** keadaan objek dunia (tanaman §4j, ternak §4k, bangunan §4n, loot/penemuan §4o, peta) tersimpan di model data terpisah dari node scene sehingga bongkar-muat chunk **tidak kehilangan keadaan**; chunk yang baru dimuat menghitung ulang keadaan dari selisih waktu (§4b, simulasi berbasis selisih hari), bukan menyimulasikan selama tak dimuat; NPC jauh tetap diturunkan dari jadwal (§4aa); objek yang sedang berinteraksi (§4v) atau terhubung quest (§4x) tidak dibongkar selama aktif.
- **Dungeon dan interior:** dimuat sebagai paket berdiri sendiri lewat Loading (instansiasi dan seed deterministik untuk dungeon acak, §4c), dengan wilayah luar disimpan secara ringan (posisi pemain, keadaan, bukan seluruh scene) dan pembongkaran sebagian chunk luar untuk memberi ruang memori; kembali ke luar memulihkan chunk di sekitar titik keluar lebih dulu. Interior sederhana yang kecil dapat memakai transisi cepat (fade pendek) bila terbukti murah dan aman.
- **Keselamatan pemain dan simulasi saat transisi:** selama Loading dunia dijeda atau pemain tidak dapat diserang; pada Streaming, musuh/NPC di cincin penyangga tidak aktif; pemain tidak boleh muncul di dalam geometri (titik masuk tervalidasi dan diperbaiki otomatis ke titik aman terdekat); aksi kritis (jual-beli, crafting) diselesaikan atomik sebelum transisi dimulai, dan transisi ditunda saat dialog/transaksi.
- **Penyimpanan dan pemulihan:** auto-save sebelum Loading yang berisiko (selaras pemicu §5a: transisi wilayah sudah termasuk simpan paksa) sehingga muat ulang aman; aplikasi masuk latar belakang saat memuat → pemuatan dijeda/dibatalkan dengan rapi dan pulih saat kembali (tidak crash, tidak setengah termuat); bila aplikasi dimatikan saat transisi, muat ulang menempatkan pemain pada titik aman terakhir yang valid.
- **Kegagalan dan batas waktu:** kegagalan muat (resource hilang/korup, memori habis) dicatat ke log dan ditangani: coba ulang terbatas → kembali ke titik aman sebelumnya → pesan terjemahan; **tidak ada layar muat tanpa batas**; batas waktu per tahap sebagai data; selaras validasi konten (§4ag).
- **Hubungan dengan update konten:** wilayah baru (§4ag) = paket data dengan tautan transisi dan syarat siap; pengujian validasi memastikan setiap tautan memiliki titik masuk valid, tujuan dapat dicapai, dan gerbang kesiapan lengkap.
- **Instrumentasi dan pengujian (D-049):** metrik dev: durasi tiap tahap transisi, frame time selama streaming, puncak memori per cincin, jumlah muat/bongkar per menit, kejadian hitch; uji otomatis headless untuk validitas tautan/titik masuk, keadaan objek tidak hilang saat bongkar-muat, tidak ada kebocoran setelah siklus muat-bongkar berulang, dan gerbang kesiapan; uji perangkat fisik menunggu laporan pengguna/tester; **angka performa dari CI atau emulator tidak dipakai sebagai klaim performa perangkat fisik.** Target durasi dan batas memori ditulis sebagai usulan sampai diukur.
Tidak ada perubahan kode atau pipeline akibat keputusan ini.

### 4ak. Implikasi Arsitektur dari D-054 (hanya catatan; belum diimplementasikan; semua angka usulan dan belum diukur)

Memperluas data lokasi/peta di §4o dan pembukaan wilayah (§4d, §4o). Prinsip: **satu sumber kebenaran data dunia**, peta/minimap/kompas hanya *tampilan* atas data itu, dan **tidak ada kebocoran informasi wilayah yang belum terbuka**.
- **Data dunia untuk peta (`MapData`):** wilayah, lokasi, dan titik fast travel sebagai resource berbasis ID stabil (§4ag): koordinat dunia, wilayah induk, jenis (desa, kota, gua, dungeon, reruntuhan, titik fast travel, objek unik, fasilitas, NPC penting), ikon (tanpa teks tertanam), kunci terjemahan id/en (§6), syarat terlihat/ditemukan/dibuka (kondisi bersama §4x, termasuk progres Progressive World Unlock D-009), dan kategori filter. Data lokasi dipakai bersama oleh peta, minimap, kompas, quest, dan pencapaian; tidak ada salinan terpisah.
- **Keadaan penemuan per pemain:** tiap lokasi/wilayah punya status (`tersembunyi → petunjuk → ditemukan → dikunjungi`), bersifat monoton (tidak mundur) dan dihitung dari event dunia (mendekati lokasi, interaksi §4v, dialog/petunjuk NPC §4y, item peta, penyelesaian quest §4x) lewat event bus (§4); disimpan sebagai bagian save modular (§5a, bagian `peta`) berversi dengan ID stabil; lokasi baru dari update konten (§4ag) muncul sebagai tersembunyi pada save lama tanpa mengubah progres. **Wilayah dan lokasi yang belum terbuka/ditemukan tidak dikirim ke tampilan** (tidak ada informasi sampai sah), sehingga peta tidak menyingkap rahasia dan tidak mengungkap spoiler; mode kabut/siluet hanya jika diputuskan.
- **Peta dunia interaktif (UI):** layar penuh di manajer konteks UI (§4r) dengan kamera 2D sendiri; **zoom dan pan** dengan sentuhan (pinch, seret, ketuk dua kali) memakai Input Action dan kepemilikan sentuhan (§4u) tanpa bentrok dengan kontrol gameplay (peta menjeda kontrol gerak/membekukan input dunia); batas zoom dan pan dikendalikan agar tetap di dalam dunia; **level detail (LOD) peta**: ikon dan label muncul menurut tingkat zoom dan prioritas, pengelompokan (clustering) saat padat, dan label dengan penghindaran tumpang tindih; target sentuh ikon cukup besar (D-045 skala UI); filter kategori; detail lokasi (nama, deskripsi, status, syarat, tindakan yang tersedia) dalam panel yang tetap terbaca di landscape. Peta dirender sebagai tekstur/atlas statis dengan lapisan penanda dinamis (hemat draw call, GL Compatibility §3); gambar peta dimuat per wilayah dan dibongkar saat ditutup (§4aj, §4ai); tanpa teks tertanam pada aset peta (lokalisasi §6).
- **Minimap:** tampilan kecil dari data yang sama: bisa berasal dari tekstur peta per wilayah/chunk (bukan render ulang adegan 3D, yang mahal pada GL Compatibility), dengan penanda di atasnya; pembaruan berkala berfrekuensi rendah (tidak tiap frame) dan hanya yang terlihat; opsi rotasi mengikuti kamera atau tetap utara (menunggu keputusan); selaras kamera adaptif (§4t: orientasi minimap konsisten dengan arah pandang); posisi, ukuran, dan transparansi dapat diatur sebagai bagian HUD (§6a, D-045) dan dapat disembunyikan sesuai konteks (§4r); tidak menutupi area permainan berlebihan (D-031).
- **Kompas dan panduan arah:** komponen HUD yang menghitung sudut dan jarak dari posisi pemain ke target aktif (objektif quest §4x, titik terdekat, tujuan yang ditandai); menampilkan penanda tepi layar atau pita kompas; pembaruan murah (perhitungan vektor saat posisi atau target berubah, bukan per frame penuh); bila rute tidak langsung (terhalang medan/air), penanda tetap menunjuk arah lurus (panduan rute otomatis hanya bila diputuskan).
- **Penanda quest dan objektif:** quest (§4x) mendaftarkan penanda lewat antarmuka `MarkerSource` (ID penanda, posisi atau area, jenis, prioritas, kunci teks, status terlihat); area objektif dapat berupa lingkaran/zona (bukan titik tepat) untuk menghindari spoiler; penanda hanya untuk quest aktif yang dilacak (satu atau beberapa, menunggu keputusan) dan hilang saat quest selesai/dibatalkan; penanda dibuat bersih (dihapus) bila quest dipulihkan atau dimigrasi (§5a); sumber lain (Guild §4d, event dunia §4p, tutorial §4ad, penanda buatan pemain, mount/kandang §4ac) memakai antarmuka yang sama; konflik atau tumpang tindih penanda diselesaikan dengan prioritas data.
- **Pelacakan posisi pemain:** penanda pemain dan arah hadap diperbarui dari posisi dunia dengan konversi koordinat dunia ke koordinat peta (sebuah transformasi per wilayah, bukan simpan duplikat); ketika pemain berada di interior atau dungeon (§4c, §4n), peta menampilkan lokasi pintu masuk, peta tingkat dungeon bila ada, atau pesan lokasi tidak dipetakan (menunggu keputusan); posisi terakhir tersimpan di save (§5a) untuk pemulihan aman (§4aj). Posisi pemain bersifat pribadi: tidak ada pelacakan/berbagi lokasi dengan pemain lain (D-014), dan tidak ada pengiriman koordinat ke server selain yang sudah ada dalam save.
- **Penemuan wilayah dan lokasi tersembunyi:** pemicu penemuan memakai ambang jarak/trigger Area3D hemat (§4ai) atau kejadian logika (dialog, item, quest), bukan polling tiap frame; wilayah baru terbuka lewat Progressive World Unlock (kondisi data §4x, D-009); notifikasi penemuan ringan (§4ae, penahan seperti §4ad) dan pencatatan ke Collection Book/Journey (§4ae); lokasi rahasia dan wilayah "spiritual" mengikuti syarat data yang sama tanpa asumsi tentang makna "spiritual" (belum didefinisikan).
- **Fast travel:** didefinisikan oleh data titik (ID, wilayah, titik muncul yang aman, syarat buka = sudah ditemukan/dikunjungi + syarat progres/quest/rank, biaya, waktu kalender yang berlalu, cooldown, larangan konteks) sehingga aturan dapat diubah tanpa kode; **validasi di klien dan (untuk operasi bernilai) di server** bila mempengaruhi ekonomi (D-050, §5b); larangan konteks: combat, dungeon, event/quest tertentu, medan/kendaraan yang tidak sesuai (§4ac), cuaca ekstrem atau kondisi cerita, bila diputuskan; kondisi pemain (mount, muatan) ditangani dengan aturan jelas; fast travel adalah **transisi Loading** (§4aj) dengan gerbang kesiapan di titik tujuan, titik tujuan tervalidasi (bukan di dalam geometri), kamera dipindah sebelum fade-in (§4t), auto-save sebelum perpindahan (§5a), dan waktu kalender yang berlalu dihitung lewat layanan kalender (§4b, §4o) sehingga musim, cuaca, jadwal NPC (§4aa), tanaman (§4j), dan event (§4p) tetap konsisten; **hanya titik yang sudah terbuka yang dapat dipilih** (daftar dan peta tidak memuat titik terkunci secara terbuka kecuali diputuskan).
- **Tap-to-move dari peta:** bila diputuskan (D-034), memilih tujuan di peta menghasilkan perintah gerak ke titik/wilayah dengan jalur bernavigasi (§4aa, §4ac) tanpa mengubah aturan akses; pemain dapat membatalkan dengan joystick (aturan §4u).
- **Pengelolaan input dan konteks:** membuka peta menjeda interaksi gameplay (§4v), menutup HUD sekunder, dan tidak membuka saat dialog/transaksi atau di situasi yang dilarang; transisi peta di UI memakai animasi ringan dan tidak memblok input lain; peta tetap dapat dibuka dari HUD dan menu (§4r); semua teks lewat kunci terjemahan id/en (§6), dengan layout menoleransi teks panjang.

## 5. Penyimpanan Progres

Implementasi awal: `game/core/save_service.gd` (autoload `SaveService`).

- Lokasi: `user://saves/slot_N.json` (penyimpanan privat aplikasi di Android), 3 slot.
- Format: amplop JSON `{schema_version, game_version, revision, updated_at_unix, checksum(SHA-256), payload_json}`.
- Tulis atomik: tulis `.tmp` → pindahkan file lama ke `.bak` → ganti. Bila file utama rusak, `load_slot` memulihkan dari `.bak`.
- `revision` naik tiap simpan → dasar deteksi konflik saat sinkronisasi.
- `schema_version` disiapkan untuk migrasi data antarversi game.
- Checksum hanya mendeteksi kerusakan, **bukan anti-curang**. Fitur online yang butuh kejujuran (ekonomi, rank) harus divalidasi server.
- Teruji otomatis di `tools/ci/smoke_test.gd` (simpan, muat, revision, pemulihan dari kerusakan).

### 5a. Implikasi Arsitektur dari D-044 (hanya catatan; belum diimplementasikan)

Memperluas §5 (fondasi lokal yang sudah ada tetap berlaku sebagai cache lokal). Detail server ada di `BACKEND_DESIGN.md` §5a.
- **Aliran data:** *state game → penulis save (event-driven) → cache lokal atomik (§5) → antrean sinkronisasi → Supabase.* Game selalu membaca dan menulis ke cache lokal; sinkronisasi berjalan di latar belakang. Bila tidak ada sesi akun/koneksi, game mengikuti desain online-only (D-014): cache menampung perubahan terbatas dan menunggu koneksi; **tidak** menjadi mode bermain offline penuh. Perilaku pada gangguan lama menunggu desain.
- **Pemicu auto-save:** penerbit event bus (§4) untuk peristiwa penting (quest §4x, inventory §4w, karakter §4e, hubungan §4z, farming §4j, dungeon §4c, mount §4ac, dll.) menandai **dirty**; penulis menggabungkan (debounce/coalescing) agar tidak menulis berlebihan, dengan **simpan paksa** saat aplikasi masuk latar belakang (`NOTIFICATION_APPLICATION_PAUSED`/focus out), saat transisi wilayah, dan saat keluar. Penulisan di luar jalur kritis (thread/ditunda ke frame lega) agar tidak mengganggu FPS; hindari hitch pada GL Compatibility (§3).
- **Skema save modular:** payload berisi **bagian per sistem** (karakter, inventory, quest, NPC/hubungan, farming/ternak, bangunan, mount, dunia/waktu, tutorial, pengaturan progres), masing-masing dengan `section_version` selain `schema_version` global; tiap sistem mendaftarkan serializer dan migrator sendiri. Amplop tetap (§5): `schema_version, game_version, revision, updated_at, checksum, payload`, ditambah `device_id`, `base_revision`, `section_revisions`. Pengaturan murni UI (tata letak tombol, volume, kamera; D-031 sampai D-034) dipisah sebagai **pengaturan pemain** dengan jalur sinkron sendiri.
- **Versioning dan migrasi:** migrasi berantai dari versi lama ke baru, dapat diuji; save dari versi lebih baru daripada game ditolak dengan pesan jelas dan **tidak ditimpa**; ID stabil (item, quest, NPC, scope) dipakai agar migrasi dapat memetakan ulang.
- **Validasi:** klien memvalidasi struktur, tipe, rentang, ukuran, dan checksum sebelum menerima data (lokal maupun cloud); data tidak valid dikarantina (tidak dimuat dan tidak menimpa data sehat). Server memvalidasi lagi (skema, ukuran maksimum, rate limit); checksum bukan anti-curang (§5), sehingga data yang memengaruhi ekonomi/rank perlu validasi sisi server (desain menunggu).
- **Pemulihan:** rantai pemulihan lokal: file utama → `.bak` → rotasi snapshot terakhir (beberapa generasi) → salinan cloud; pemulihan otomatis diberi tahu ke pemain; sebelum menimpa save apa pun karena migrasi/konflik dibuat cadangan; cadangan cloud berversi dengan batas retensi (belum diputuskan).
- **Sinkronisasi:** `push_save` (kirim perubahan setelah `base_revision`) dan `pull_save`; sinkron saat dimulai, secara berkala/pada peristiwa penting, dan saat kembali ke aplikasi. **Retry dengan exponential backoff + jitter dan batas jumlah percobaan**; status antrean dan kegagalan tampil di indikator; setelah batas wajar, data tetap aman di cache dan menunggu pemicu berikutnya.
- **Konflik:** deteksi lewat `base_revision` dan `device_id` (§BACKEND §5): server menolak bila `base_revision` ≠ revisi server dan mengembalikan snapshot server. Resolusi **tidak pernah diam-diam** dan tidak menimpa progres lebih baru: (1) bila hanya satu sisi berubah → fast-forward; (2) bila keduanya berubah → perbandingan **per bagian** dan, hanya untuk bagian yang aman digabung (mis. penambahan koleksi/riwayat monoton, pengaturan), gabung otomatis; (3) selain itu **pemain memilih** (lokal/cloud) dengan ringkasan perbedaan (waktu bermain, hari game, progres utama) dan cadangan sisi yang tidak dipilih. Data yang tidak kompatibel (versi skema berbeda, ID tak dikenal) tidak digabung. Aturan rinci menunggu desain.
- **Duplikasi transaksi:** tiap operasi yang mengubah nilai penting (hadiah quest, pembelian/penjualan, drop langka) membawa **ID transaksi/idempoten** (UUID dari klien) yang disimpan dalam payload dan dicatat server (jendela waktu), sehingga pengiriman ulang akibat retry atau pemulihan tidak mengganda; penerapan hasil save yang dimuat tidak menjalankan ulang efek (hadiah hanya diberikan sekali).
- **Konsistensi atomik:** satu snapshot konsisten lintas sistem (dibekukan pada satu titik antar-frame, bukan di tengah transaksi seperti jual-beli/crafting); penulisan lokal tetap atomik (.tmp → .bak → ganti); tidak ada save sebagian yang dianggap sah.
- **Keamanan:** akun hanya dapat membaca/menulis datanya sendiri lewat **Row Level Security** (`user_id = auth.uid()`) pada semua tabel save; klien hanya memakai kunci publik (anon) dan token sesi; **kunci service-role/rahasia tidak pernah** ada di aplikasi atau repo (GitHub Secrets/pengaturan penyedia saja, sesuai SIGNING_GUIDE dan BACKEND_DESIGN §6); semua lalu lintas TLS; token sesi disimpan di penyimpanan privat aplikasi; tidak ada kredensial di source code; rate limit dan batas ukuran payload di server; pengujian kebijakan RLS (akses lintas akun harus ditolak) wajib sebelum rilis.
- **Waktu:** tanggal game dan seed bukan jam perangkat (§4b); timestamp sinkronisasi memakai waktu server sebagai acuan urutan, sehingga mengubah jam perangkat tidak memanipulasi revisi/konflik.
- **Indikator UI:** status ringkas (tersimpan, menyimpan, menunggu koneksi, tersinkron, konflik, error) sebagai komponen global (D-031, §4r); pesan lewat kunci terjemahan id/en (§6); konflik dan pemulihan memakai dialog yang jelas dengan target sentuh nyaman.
- **Integrasi:** semua sistem progres mendaftarkan bagian save lewat antarmuka serializer yang sama; tidak ada sistem yang menulis langsung ke file/cloud.
- **Pengujian:** uji headless untuk serialisasi-migrasi tiap bagian, tulis atomik dan pemulihan berlapis, debounce/simpan paksa, idempotensi transaksi, retry dan batas, skenario konflik (satu sisi/dua sisi/tak kompatibel), penolakan save dari versi lebih baru, serta uji kebijakan RLS pada lingkungan uji; tidak ada tes yang membutuhkan rahasia produksi.
Tidak ada perubahan kode atau pipeline akibat keputusan ini.

Pengerasan klien (obfuscation/deteksi root) tidak dijadikan andalan; tidak ada pemeriksaan intrusif terhadap perangkat/privasi tanpa keputusan.

- **Security monitoring:** metrik dan peringatan dari layanan (tingkat penolakan validasi, lonjakan permintaan/kesalahan, percobaan akses ditolak RLS, pola transaksi ganda, anomali waktu, rasio pemulihan), dasbor sederhana dan peringatan ke pengelola; ambang dan responder menunggu keputusan; selaras pemantauan crash/performa (§4ag, §10a) dengan aturan privasi; rate limit dan batas ukuran di server; perlindungan penyalahgunaan sumber daya.
- **Integrasi dengan sistem lain:** validasi memakai definisi data bersama (item §4g, quest §4x, achievement §4ae, kosmetik §4af, ekonomi §4h); idempotensi transaksi (§5a) adalah fondasi anti-duplikasi; `StoreService` (§4af) memverifikasi tanda terima di sisi server; pencabutan kosmetik/kepemilikan hanya lewat jalur server beraudit; migrasi (§4ag) harus lulus validasi yang sama (aturan validasi berversi bersama `content_version`, agar konten baru tidak ditolak keliru dan save lama tetap valid).
- **Biaya dan keadilan:** semua mekanisme adalah fitur dasar tanpa biaya untuk pemain dan **tidak menjadi produk monetisasi**; pengelola menanggung biaya layanan, sehingga desain memilih validasi yang **hemat** (validasi ringan di setiap push, pemeriksaan berat hanya pada operasi bernilai tinggi atau saat anomali), dengan estimasi biaya dan batas paket layanan dihitung saat implementasi (bagian dari persiapan operasional).
- **Pengujian (D-049):** uji otomatis untuk invarian dan penolakan (data malformed, lonjakan, ID duplikat), uji RLS lintas-akun (harus ditolak), uji idempotensi, uji migrasi dengan aturan validasi berversi, uji audit log (peristiwa tercatat, tanpa data pribadi berlebih), pemindaian rahasia, dan uji negatif (klien palsu); rilis menunggu lulusnya uji keamanan sebagai bagian release gate (§10a).

- **Keamanan:** uji kebijakan RLS lintas-akun wajib sebelum rilis (§5a); pemindaian rahasia di repo (mencegah kredensial masuk source, DEVELOPMENT_RULES §7); uji transaksi/tanda terima dengan data uji saat toko diimplementasikan (§4af).
- **Pelaporan crash/telemetri:** menunggu keputusan privasi, persetujuan, dan akun (P-006, PENDING); tidak ada asumsi di sini.
- **Pembaruan dokumen:** hasil uji perangkat fisik dicatat di `PROGRESS_LOG.md` (aturan yang sudah ada) dengan sumber bukti; `TESTING_APK.md` tetap panduan uji dev.
Tidak ada perubahan kode atau pipeline akibat keputusan ini.

## 11. Risiko Teknis

| Risiko | Mitigasi |
|---|---|
| Performa 3D di HP menengah | Anggaran performa §3; uji perangkat nyata sejak vertical slice |
| Ukuran APK/memori untuk dunia besar | Region sebagai unit muat; kompresi tekstur; pantau ukuran tiap rilis |
| Kehilangan/bocor kunci rilis | Panduan `SIGNING_GUIDE.md`; cadangan di luar repo; CI menolak rilis bertanda kunci dev |
| Backend terkunci pada satu vendor | Antarmuka `BackendClient`; data inti portabel (Postgres/JSON) |
| Layar boot di HP nyata belum teruji | Menunggu laporan pemilik (TESTING_APK.md) |
